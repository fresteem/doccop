# AGENTS.md

Tool-agnostic instructions for coding agents (Claude Code, Codex, Cursor, Aider, etc.) working on this repository. Follows the [agents.md](https://agents.md) convention.

Tool-specific deep guides:
- `CLAUDE.md` — Claude Code overview

## Project context

**doccop** is an MIT-licensed, OSS document-generation engine published as `@doccop/*` on npm. It turns `.docx` templates into rendered documents via pluggable variable resolution and per-subtype "requisites" block injection. Database-agnostic, framework-agnostic.

**Status:** `0.1.0-alpha.0` — Wave 1–8 done. Roadmap targets v1.0 stable.

## Setup

```bash
cd doccop          # repo root (contains package.json)
npm install        # workspaces install
npm run build      # tsc across all packages
npm test           # vitest run (~235 tests)
```

Requires Node ≥ 20, npm ≥ 10.

## Package layout

```
@doccop/core              Pure engine. No I/O. Deps: pizzip + xmldom only.
@doccop/server            Fastify plugin over the engine. Defines store interfaces.
@doccop/storage-postgres  Drizzle-backed reference stores + FilesystemBlobStorage.
@doccop/headless          (Planned) Framework-agnostic UI primitives — state
                          machines, DOM selection→WrapLocation mapper, anchor
                          map utilities. No React, no DOM, no CSS.
@doccop/react-ui          (Planned) React adapter — hooks + render-props +
                          unstyled primitives over @doccop/headless.
demo-app                  (Planned) Fastify + Postgres standalone example.
```

Vue/Svelte/Solid adapters are **community territory** — the public API of `@doccop/headless` is stable enough for any framework to wrap. We do not ship those packages.

**Dependency direction is one-way:** `core` knows nothing about `server`; `server` knows core types; `storage-postgres` knows both; `headless` knows core types only; `react-ui` depends on `headless` + core types. Never reverse this.

## Hard constraints (do not violate)

### Public API surface is frozen until v1.0

Every type in `packages/core/src/types.ts`, `packages/core/src/errors.ts`, and `packages/server/src/types.ts` is part of the published contract. Adapters in consumer applications implement these — any breaking change forces a major-version bump.

You may **add** optional fields, new methods with default-no-op semantics, and new error codes. You may **never** rename, remove, or tighten an existing public symbol in a non-major release.

**Mechanical guard:** every package ships an `etc/<package>.api.md` snapshot generated by `@microsoft/api-extractor`. CI regenerates and diffs. If your PR changes that file, the workflow fails until either (a) you revert the change or (b) you explicitly approve via the `breaking-change` PR label and add a `docs/migrations/<X.Y-to-X.Y+1>.md` entry.

This applies equally to:
- HTTP route paths and request/response shapes (`/v1/*`)
- HTTP status codes mapped from each `DocCopErrorCode`
- The `w14:paraId` discipline (8-char uppercase hex)
- The SDT XML structure emitted by `PlaceholderEngine.wrap`
- The `requisites:party_X` tag format
- Storage path conventions returned by `StorageAdapter` impls

When in doubt: would an existing host need to change adapter code? If yes — major bump.

### License: MIT-only, transitively

Every dependency (direct + transitive) must be MIT / BSD-2 / BSD-3 / Apache-2.0 / ISC. Dual-licensed (e.g. `pizzip` is MIT/GPL-3): explicitly choose the permissive license and note it in CHANGELOG.

**Banned:**
- AGPL anywhere in the dependency tree
- "Free for non-commercial use" libraries
- Commercial docxtemplater modules (the MIT core is fine; paid modules are not)

Before adding a new dependency: read its `LICENSE` file, check `package.json#license`, note the license string next to the entry in CHANGELOG.

### Approved docx library set

Stay on **`pizzip` + `@xmldom/xmldom` + `mammoth`** for OOXML work. Any proposal to swap to a "modern" alternative (ESM-native, Web Worker–based, etc.) must pass explicit license review first — the majority of newer docx libraries are commercial or AGPL.

### Security defaults (do not weaken without CHANGELOG note)

- XML parsing rejects `<!ENTITY` declarations (XXE guard in `parseXmlSafely`)
- Filesystem storage validates paths against owner + UUID convention
- Idempotency keys are namespaced by `(key, user_id)` — two users sharing a key see distinct rows
- HTML preview escapes every dynamic value (incl. `<`/`>` in attributes)
- Engine limits: 10 MiB template, 5 MiB snippet, 500 placeholders, 30 s render timeout
- npm publish uses `--provenance` with sigstore

## Code style

- TypeScript 5, strict mode + `noUncheckedIndexedAccess` + `exactOptionalPropertyTypes`. No `any`.
- ESM only. `"type": "module"` everywhere. Import specifiers use `.js` extension (NodeNext requirement).
- Biome (not ESLint/Prettier) is the source of truth. Run `npm run format` before committing.
- No default exports outside `*.config.ts` (Biome enforces).
- Always `import type` / `export type` for type-only references (Biome enforces).
- Errors are typed: subclass `DocCopError` from `@doccop/core/errors`. Never `throw new Error("...")` in production code.
- Public functions get TSDoc. Internal helpers get short prose explaining *why*, not *what*.

## Observability

- **No direct `console.*` in production code.** Use the injected `Logger` interface (passed via `DocCopConfig.logger`). Default is a no-op logger; hosts inject pino/winston/etc.
- Log levels follow the `Logger` contract: `trace` / `debug` / `info` / `warn` / `error`. The engine emits `info` for major lifecycle events (render start/end), `warn` for non-strict render warnings, `debug` for placeholder routing details.

## Internationalization of error messages

- `DocCopError.message` stays **English-only** — it is for developer logs and stack traces, not for end users.
- The user-facing translation key is `DocCopError.code` (e.g. `"ABSENT_VALUE_IN_STRICT_MODE"`).
- `DocCopError.details` is a frozen, JSON-serializable record — hosts use it as the parameter bag for their i18n templates.
- Hosts that need localized end-user messages map `code` → translated string client-side, interpolating `details`. The engine never imports an i18n library.

## Testing rules

- **Programmatic fixtures only** in unit/integration tests — see `packages/core/test/fixtures/fixtureBuilder.ts`. Do not commit binary `.docx` files to the unit-test paths.
- **Real-world `.docx` corpus** lives under `test/fixtures/real/` (planned) for parser stability tests. These are real Word-authored files; round-trip and parse them as part of the v1.0 readiness gate.
- New public function → lands with tests for happy path AND every rejection branch.
- Bug fix → lands with a regression test that fails on the buggy code and passes after.
- Tests run in-memory: no Docker, no real DB, no real network. Postgres integration is host-side.

## Don't

- Don't import from outside the `doccop/` repo. Each package is self-contained.
- Don't assume a database, a storage backend, or a specific host in `core` or `server`. If you find yourself writing SQL in core or server — wrong package.
- Don't introduce global mutable state. The engine is reentrant; concurrent renders coexist in one process.
- Don't change SDT XML structure (tag/alias/lock/sdtContent) — existing hosts have templates persisted with this exact XML.
- Don't widen the `DocCopErrorCode` union without checking every status-mapping branch in `packages/server/src/middleware/errors.ts`.
- Don't publish without bumping versions + updating `CHANGELOG.md`.
- Don't force-push to `main`. The release workflow checks out `main`; rewriting history breaks every consumer pinned to a SHA.

## Pull request checklist

- [ ] `npm run lint && npm run build && npm test` all pass locally
- [ ] `npm run api:check` passes (api-extractor snapshots unchanged), OR PR has `breaking-change` label + migration note
- [ ] New deps: license verified (MIT / BSD / Apache-2.0 / ISC only), noted in CHANGELOG with the license string
- [ ] Public API surface unchanged (or major-version bump justified in PR description)
- [ ] CHANGELOG entry under `[Unreleased]` describes Added / Changed / Fixed / Security
- [ ] Tests added for happy + rejection paths; real-world `.docx` corpus run if parser/renderer touched
- [ ] JSDoc on new public symbols
- [ ] If breaking change: `docs/migrations/X.Y-to-X.Y+1.md` populated from `docs/migrations/TEMPLATE.md`
